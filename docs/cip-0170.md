# CIP-0170 — On-Chain Identity & Attestation

This is the **new integration** built on top of the validated **Godot × Cardano
TRL5 baseline**. It does **not** replace the existing Godot → Cardano testnet
flow; it extends it with a verifiable identity/attestation layer.

## Required target architecture (implemented)

```
Godot gameplay
  → player wallet / game profile
  → qualifying gameplay milestone
  → backend validation (player registered, milestone fields valid)
  → CIP-0170 attestation creation/update (signed W3C VerifiableCredential)
  → Cardano transaction (anchor, metadata label 1701)
  → on-chain verification (hash match + issuer signature valid)
  → verified achievement/progression displayed in Godot
```

## State separation (required by the spec)

| # | Layer | Where | Contents |
| - | ----- | ----- | -------- |
| 1 | Normal off-chain game state | backend in-memory profile map | player profile linked to Cardano wallet |
| 2 | CIP-0170 identity/attestation state | signed W3C VerifiableCredential (off-chain, held by Godot/backend) | issuer AID, subject, claim, status, version |
| 3 | Cardano transaction evidence | on-chain metadata **label 1701** (source of truth) | attestationHash, issuer, subject, status, version, timestamp |

High-frequency gameplay stays off-chain. Only qualifying milestones produce an
attestation + transaction.

## Issuer identity — KERI-style AID

The attestation issuer is identified by a **KERI-style Self-Addressing Identifier
(SAID)**:

```
AID = E + base64url( blake2b-256( "LAB3:CIP0170" || issuer_ed25519_public_key ) )
```

It is deterministic from the issuer key (the bridge wallet), self-addressing, and
referenced in every attestation (`issuer`) and on-chain anchor (`issuer`).

## Attestation (W3C VerifiableCredential)

```json
{
  "@context": ["https://www.w3.org/2018/credentials/v1"],
  "id": "did:cardano:<player_address>#<achievement>-v<version>",
  "type": ["VerifiableCredential", "GameAchievementAttestation"],
  "issuer": "<KERI AID>",
  "issuanceDate": "<ISO 8601>",
  "version": 1,
  "status": "created",
  "credentialSubject": {
    "id": "did:cardano:<player_address>",
    "playerName": "Alice",
    "achievement": "quest_001",
    "event": "quest_completed",
    "questId": "quest_001",
    "tier": 3,
    "progression": "achievement"
  }
}
```

The canonical attestation is hashed (`blake2b-256` of a stable JSON serialization)
and **signed by the issuer** with a **CIP-8 Ed25519 signature**
(`wallet.signData`). Updates increment `version` and set `status: "updated"`.

## On-chain anchoring (label 1701)

```json
{
  "tag": "LAB3_CIP0170",
  "attestationHash": "<blake2b-256 of canonical attestation>",
  "issuer": "<KERI AID>",
  "issuer_addr_a": "<first 54 chars of issuer address>",
  "issuer_addr_b": "<rest of issuer address>",
  "subject_a": "<first 54 chars of player address>",
  "subject_b": "<rest of player address>",
  "achievement": "quest_001",
  "event": "quest_completed",
  "status": "created",
  "version": 1,
  "timestamp": "<ISO 8601>"
}
```

- Full addresses exceed Cardano's 64-byte metadata string limit, so they are split
  into `_a`/`_b` fields (concatenate to recover).
- The same transaction also carries the Catalyst pilot message tag under **label
  674** (`tag: LAB3_GODOT_CARDANO_TESTNET`).
- The on-chain anchor is the **source of truth**; the full VC + signature are
  exchanged off-chain (matching CIP-0170's "hash anchored, credential off-chain"
  model).

## Verification

`POST /api/attestation/verify` with `{ txHash, attestation, signature, key, issuerAddr }`:

1. Reads the **on-chain anchor** (label 1701) for `txHash` via Koios.
2. Recomputes `blake2b-256(attestation)` and compares to `anchor.attestationHash`.
3. Verifies the **CIP-8 Ed25519 signature** over that hash using `checkSignature`.
4. Returns `verified: true` only when both hold — Godot then displays the
   achievement as verified.

## API

| Endpoint | Purpose |
| -------- | ------- |
| `POST /api/player/register` | Link a player profile to a Cardano wallet (off-chain state). |
| `POST /api/attestation/create` | Validate milestone → create attestation v1 → sign → anchor → return tx hash. |
| `POST /api/attestation/update` | Update the attestation (version+1, status `updated`) → anchor → return tx hash. |
| `POST /api/attestation/verify` | On-chain hash match + signature verification. |
| `GET  /api/attestation/onchain/:txHash` | Read the raw on-chain anchor (label 1701). |

## Error handling

- Invalid/empty player addresses are rejected (must be `addr_test1…`).
- A bridge wallet with no UTxOs fails with a clear funding message.
- Rapid create→update retries automatically when the previous tx consumed the
  UTxO ("all inputs spent").
- Verification fails gracefully with a `reason` string when the anchor is missing
  or the hash/signature does not match.

## Baseline vs. new integration

- **Existing TRL5 baseline (unchanged):** Godot app, GitHub Pages web build, hosted
  bridge, repeatable Preprod transactions (metadata 674), CIP-68 achievement NFTs.
- **New CIP-0170 integration (this doc):** player identity registration, KERI-AID
  issuer, signed W3C VerifiableCredential attestations, on-chain anchoring
  (label 1701), and on-chain verification.
